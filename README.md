# Sports Club Hub

A lightweight community sports directory built with **C#, ASP.NET Core Blazor (.NET 8), Entity Framework Core and SQLite**.
Residents can browse sports, clubs and venues and register their interest in playing a sport. Administrators manage the
directory and see aggregate statistics. It is designed to be understandable to a junior developer and structured so that
municipal integration can be added later.

> **Status:** first version. Read [Verification status](#verification-status) before relying on it. The project was written
> and compile-checked in an environment without NuGet access, so it has **not** yet been run end to end.

## Prerequisites

- [.NET 8 SDK](https://dotnet.microsoft.com/download) (the project targets `net8.0`, a long-term-support release; it can be retargeted to a newer SDK by changing `TargetFramework` in the three `.csproj` files)
- Internet access for the first `dotnet restore` (NuGet)
- Optional: `dotnet tool install --global dotnet-ef` (only if you want migrations)

## Run it

```bash
unzip SportsClubHub.zip && cd SportsClubHub
dotnet restore
dotnet build
dotnet test                                   # runs the unit tests
dotnet run --project src/SportsClubHub.Web    # opens http://localhost:5080
```

In Development the app creates the database, the starter sports list, **fictional demonstration data**, and an
administrator account. Because no password is stored in the code, the administrator password is **generated and printed once in the
console** the first time the app starts:

```
Development administrator created. Sign in with admin@example.test and password <random>
```

Sign in at **Staff sign in** (`/account/login`). To choose your own credentials instead, set them before the first run:

```bash
cd src/SportsClubHub.Web
dotnet user-secrets init
dotnet user-secrets set "Admin:InitialEmail" "you@yourdomain.example"
dotnet user-secrets set "Admin:InitialPassword" "a-long-passphrase-of-10-or-more-characters"
```

In production, supply `Admin__InitialEmail` and `Admin__InitialPassword` as environment variables and set
`Database__LoadDemoData=false` (the default). Admin credentials are only used when no administrator exists yet.

For local configuration, copy `.env.example` to `.env` and replace the placeholders. ASP.NET Core does not load
`.env` files by itself, so import the values into the process before starting the app. In PowerShell:

```powershell
Get-Content .env | Where-Object { $_ -and -not $_.StartsWith("#") } | ForEach-Object {
    $name, $value = $_ -split "=", 2
    [Environment]::SetEnvironmentVariable($name, $value, "Process")
}
dotnet run --project src/SportsClubHub.Web
```

The application currently uses EF Core SQLite. `MONGODB_URI` is stored as a prepared placeholder for a future
MongoDB data-layer migration; it must not replace `ConnectionStrings__DefaultConnection` until that migration is completed.

## Database

- SQLite file: `src/SportsClubHub.Web/App_Data/sportsclubhub.db` (change `ConnectionStrings:DefaultConnection` to move it).
- On startup the app calls `EnsureCreated()`, which builds the tables **only if the database does not exist**. It never drops
  or deletes data. Seed steps only run when the relevant tables are empty.
- **Safely reset the development database:** stop the app, delete the `App_Data` folder, start the app again.
  Never do this to a database holding real data.
- **Why not migrations yet?** Migration files must be generated by the `dotnet ef` tool, which needs NuGet access, and could not be
  generated where this project was written. `EnsureCreated` does not update an existing database when the model
  changes. Once you have a working build, switch to migrations:
  ```bash
  dotnet ef migrations add InitialCreate --project src/SportsClubHub.Web
  ```
  then replace `db.Database.EnsureCreatedAsync()` in `Data/DatabaseInitializer.cs` with `db.Database.MigrateAsync()`, and delete the
  old development database once.

## Domain model

| Class | Why it exists |
|---|---|
| `Sport` | A type of sport, stored as a database row so new sports need no code change. Has a `SportCategory`. |
| `Club` | An organisation. `VerificationStatus` (Pending/Verified/Rejected) keeps unchecked clubs out of the public directory. |
| `ClubSport` | Explicit join: a club offers many sports and a sport is offered by many clubs. Key = (ClubId, SportId). |
| `Team` | Belongs to one `Club` and one `Sport`. Rule: a club can only field a team in a sport it offers. |
| `Venue` | A facility. |
| `VenueSport` | Explicit join: a venue supports many sports and a sport is played at many venues. |
| `Participant` | A resident who registered interest. Holds only name, e-mail, area, optional phone, and consent time. Never listed publicly. |
| `SportInterest` | "This participant is interested in this sport". Key = (ParticipantId, SportId), so duplicates are impossible. |
| `AdminUser` | A staff account (password hash only). |

**Interest, application and membership are different things.** `SportInterest` is only interest. It is not an application and not a
membership. Membership should be a separate `ClubMembership` entity with its own status when it is needed. The
insights pages always say "interest registrations".

**Deliberately not built:** `ClubMembership`, `Booking` and `Championship`. The brief said to add them only if they could be done
properly within scope. They are natural next steps.

## Architecture

```
src/SportsClubHub.Domain   Plain C# entities, enums, validation attributes, input-cleaning helpers. No dependencies.
src/SportsClubHub.Web
  Data/                    AppDbContext (EF Core configuration), SeedData, DatabaseInitializer
  Services/                One small service per area: Sport, Club, Team, Venue, ParticipantInterest, Insights, AdminAccount
  Models/                  Form models that are not entities (ParticipantInterestForm)
  Components/Pages/        Public pages; Pages/Admin = administration; Pages/Account = sign in/out
  Components/Shared/       Reusable pieces (page header, sport check boxes, admin tabs)
  Program.cs               Dependency injection, authentication, pipeline
tests/SportsClubHub.Tests  xunit tests (SQLite in memory)
```

Design choices that are worth knowing:

- **Services, not logic in pages.** Pages call services; services own queries and business rules.
- **`IDbContextFactory`.** Blazor Server keeps a connection open for a long time, so each operation creates a short-lived `DbContext`.
- **Validation lives once**, as data annotations on the entities (or the form model), reused by every form. Services re-check rules the
  browser could skip (consent, "club offers this sport", duplicates).
- **Public vs admin.** Public pages only see `Verified` + active clubs. Admin pages require the `Administrator` role.
- **Render modes.** Searching/editing pages are interactive (Blazor Server). Home, privacy and sign in/out are plain server-rendered
  pages, because only a normal HTTP request can set the sign-in cookie.

## Features

- Sports directory: search by name, filter by category, detail page (with clubs, venues), admin add/edit/deactivate
- Sport imagery: administrators can add durable HTTPS image URLs (for example from Cloudinary, Supabase Storage or S3) to show sports in action
- Club directory: search by name/location, filter by sport, detail page with teams and the club's own contact details, public registration form (starts as *Pending*), admin verify/reject/edit/deactivate and team management
- Participant interest registration with validation, mandatory adult and privacy-notice confirmations, duplicate prevention, and matching clubs shown afterwards
- Venue directory: filter by location and sport; admin add/edit/deactivate with supported sports
- Insights (public, aggregate only): counts, most popular sports, sports with interest but few clubs, clubs and people by location
- Staff sign in with cookie authentication, hashed passwords, role-based authorisation on all `/admin` pages
- Privacy notice page (a template to be completed by the operator)

## Privacy and security (POPIA-minded, not a compliance claim)

This application applies privacy-conscious defaults. **That does not make it POPIA-compliant.** The operating organisation must complete the privacy
notice, appoint an Information Officer, define retention and deletion procedures, and take legal advice.

- Only necessary data is collected; no children's details (adults only, confirmed by the participant)
- Participant details are never shown on a public page, and no admin screen lists individuals
- Location breakdowns of people are hidden until a group has at least 3 people
- Sign-up responses are identical for new and returning e-mails, so the form cannot be used to test whether an address is registered
- Input is trimmed and normalised; e-mails are stored lower case; passwords are hashed; no secrets in the repository; the database is never wiped at startup
- Authorisation is enforced by `[Authorize(Roles = "Administrator")]` on every admin page, not by hiding links
- Demo data is fictional: `example.test` e-mail addresses, "Demo Participant NN" names, and descriptions starting `[Demo data]`

## Known limitations

- **Not yet run end to end** (see below)
- Schema creation uses `EnsureCreated`, not migrations (instructions above)
- No e-mail verification: someone could register interest using another person's address. No CAPTCHA or rate limiting on public forms or sign in; no account lockout
- Admin authorisation is enforced on pages. Services are not individually guarded, so any new page that uses them must carry `[Authorize]`
- Only one role (`Administrator`). A read-only municipal role (aggregate data only) is the intended next step
- No way yet to export or erase a participant on request (the database is set up to cascade deletes when that is built)
- Location is free text with suggestions, so spelling differences can split a location in the statistics
- Club registration is unauthenticated (protected only by the Pending → Verified step)

## Verification status

Written in a sandbox where NuGet could not be reached, so **EF Core packages could not be restored**. What was and was not verified:

| Check | Result |
|---|---|
| Domain project builds | Verified (real build) |
| Entire web project (C#, all Razor pages, services) compiles | Verified **against a hand-written stub of the EF Core API**, not against real EF Core. This catches type, syntax and Razor errors, but not mistakes only real EF Core would find |
| Validation and normalisation rules (consent boxes, blank optional fields, bad e-mail/URL/phone/capacity) | Verified by running them (11 checks, all passed) |
| `dotnet restore` with real packages | **Not run** |
| EF Core model, relationships, SQL translation of queries, database creation, seeding | **Not run** |
| The xunit tests in `tests/` | **Written, not compiled, not run** |
| Running the site: sign in, forms, filters, admin pages | **Not run** (no browser, no database) |

Please run `dotnet restore && dotnet build && dotnet test` first and report any errors. The most likely failures are small EF Core query translation issues or test setup
issues, since those are exactly what could not be exercised here.
